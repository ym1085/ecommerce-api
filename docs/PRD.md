# PRD: farm-market-platform

## 1. 제품 목표

중소 규모 B2C 쇼핑몰의 백엔드 REST API를 제공한다.
구매자는 회원가입과 로그인 후 상품을 탐색하고 장바구니, 주문, 결제, 배송 조회로 이어지는 구매 흐름을 이용한다.

## 2. 사용자와 권한

| 사용자 | 할 수 있는 일 |
| --- | --- |
| 비회원 | 회원가입, 로그인, 상품 목록·상세 조회 |
| 회원 | 비회원 기능, 본인의 회원·배송지·장바구니·주문·결제·배송 정보 이용 |
| 관리자 | 관리자 전용 상품 관리 API 이용 |

- 회원은 다른 회원의 정보를 조회하거나 변경할 수 없다.
- 관리자 API는 `ADMIN` 역할만 접근할 수 있다.

## 3. 기능 요구사항

### 3.1 인증·회원

- 이메일과 전화번호는 중복 가입할 수 없다.
- 비밀번호는 단방향 암호화하여 저장한다.
- 활성 회원만 로그인할 수 있다.
- 로그인 성공 시 Access Token과 Refresh Token을 발급한다.
- 재발급은 유효한 Refresh Token과 Redis 저장 정보가 일치할 때만 허용한다.
- 로그아웃 시 Refresh Token을 삭제하고 남은 유효기간 동안 Access Token을 차단한다.
- 회원은 본인 정보와 배송지를 조회·등록·수정·soft delete할 수 있다.

### 3.2 상품

- 상품 목록은 페이징하며 대표 이미지 한 건을 포함한다.
- 상품 상세는 상품 정보와 `displayOrder` 순서의 전체 이미지 목록을 포함한다.
- DB에는 이미지 경로만 저장하고 응답 시 환경별 base URL과 조합한다.
- 관리자 상품 생성·수정·상태 변경의 상세 요구사항은 구현 전에 확정한다.

### 3.3 장바구니

- 회원은 주문 가능한 상품을 장바구니에 추가할 수 있다.
- 동일 상품을 다시 추가하면 별도 행을 만들지 않고 수량을 갱신한다.
- 장바구니 조회는 현재 상품 가격·상태·재고를 기준으로 응답한다.
- 회원은 본인의 장바구니 수량만 수정하거나 항목을 삭제할 수 있다.

### 3.4 주문

- 주문은 인증된 회원과 한 개 이상의 주문 상품으로 생성한다.
- 동일 주문에 같은 상품을 중복 입력할 수 없다.
- 주문 생성 시 상품 존재 여부, 판매 상태, 재고를 검증한다.
- 재고 검증·차감과 주문 저장은 하나의 트랜잭션으로 처리한다.
- 동시 주문은 상품 ID 오름차순 비관적 잠금으로 재고 정합성과 데드락 위험을 제어한다.
- 주문 목록은 본인 주문만 페이징 조회하고, 상세도 본인 주문만 조회한다.
- 주문 시점의 상품명·가격·수량은 주문 항목에 보존한다.

### 3.5 결제·배송

- 회원은 본인 주문의 결제 상태와 배송 상태만 조회할 수 있다.
- 결제 성공 전후의 주문·결제 상태 전이와 중복 요청 처리 기준은 결제 기능 구현 전에 ADR로 확정한다.
- 외부 PG 연동 방식, 실패 보상, 웹훅 검증 방식은 현재 미결정이다.

## 4. 기능 현황

이 표는 요구사항의 구현 현황을 나타내며, 상세 판단은 실제 코드를 우선한다.

| 영역 | 현재 상태 |
| --- | --- |
| 회원가입·로그인·재발급·로그아웃 | 구현 |
| 상품 목록·상세와 이미지 조회 | 구현 |
| 주문 목록·상세 | 구현 |
| 주문 생성 API | Service 구현, API 미완료 |
| 배송지·장바구니·결제·배송 API | 미구현 |
| 관리자 상품 API | 골격만 존재, 요구사항 미확정 |
| 프론트엔드 | 범위 외 |

## 5. 현재 범위 외

- 리뷰·평점
- 전문 검색 엔진을 사용한 상품 검색
- 쿠폰·할인·포인트
- 이메일·SMS·푸시 알림
- 소셜 로그인

## 6. 공통 완료 조건

- API URL, HTTP 메서드, 상태 코드는 프로젝트 API 규약을 따른다.
- 요청 DTO는 Bean Validation으로 검증하고 Entity를 응답에 노출하지 않는다.
- 목록 API는 페이징하고 연관 조회에서 N+1과 부모 행 중복을 만들지 않는다.
- 인증 API를 제외한 회원 데이터는 인증된 본인의 리소스로 제한한다.
- 주요 성공·실패 분기의 Service·Controller 테스트가 통과한다.
- 모듈별 빌드와 테스트 명령이 성공한다.

## 7. 하네스 적용 기준

- Step은 이 문서의 기능 요구사항 하나 이상을 Acceptance Criteria로 연결한다.
- 요구사항과 현재 코드가 충돌하면 임의로 구현하지 말고 충돌 내용을 보고한다.
- 결제처럼 미결정 사항이 결과를 바꾸면 해당 구현 Step을 만들기 전에 사용자 결정을 받거나 `blocked`로 처리한다.
